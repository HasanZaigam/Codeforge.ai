# CLAUDE.md — Platform repository

This file governs work **on this repository** — the Autonomous Software Development Platform product itself. It does not apply to, and is never loaded during, task execution against a *connected project's* codebase (e.g. OTT, E-True, XYZ). See [docs/CONTEXT_ARCHITECTURE.md](./docs/CONTEXT_ARCHITECTURE.md) for why that separation exists and is enforced.

## What this product is

Read [docs/PRODUCT_VISION.md](./docs/PRODUCT_VISION.md) first. One sentence: the platform takes a plain-language task, autonomously drives it through investigation, implementation, testing, self-fix, and independent review against a connected project's real repository, and interrupts a human only when a genuine decision is required.

## Ground rules for working in this repo

- **Platform vs. Project stays separate.** Never add project-specific logic, credentials, or context (for OTT, E-True, or any connected project) into this repository. Project-specific behavior belongs in that project's own repo/config, discovered through the adapters defined in [docs/INTEGRATION_ARCHITECTURE.md](./docs/INTEGRATION_ARCHITECTURE.md).
- **Interfaces before implementations.** Any new coding engine, source-control provider, or deployment provider must implement the existing abstraction (`CodingEngineAdapter`, `SourceControlProvider`, `DeploymentAdapter`) — never bypass it with vendor-specific calls from core logic.
- **Orchestrator stays deterministic.** Task state transitions are rule-based; don't route control-flow decisions through an LLM call.
- **No secrets in code, prompts, or context files.** See [docs/SECURITY_ARCHITECTURE.md](./docs/SECURITY_ARCHITECTURE.md).
- **Don't add agent roles casually.** The two-role design (Implementer, Reviewer) was a deliberate rejection of a larger multi-agent design — see [docs/AGENT_ARCHITECTURE.md](./docs/AGENT_ARCHITECTURE.md) before proposing a new one.
- **MVP boundary is intentional, not incomplete.** Before adding a capability, check [docs/MVP_SCOPE.md](./docs/MVP_SCOPE.md) — an item listed "out of scope" was excluded deliberately, not forgotten.

Phase 4D.1: multi-intent Chat — a single message naming several supported questions at once ("how many are Done, which are in Review, and what's blocking the oldest Review task?") is now split into clauses, each classified/executed independently, and composed into ONE answer, instead of only answering the first matching clause (see [docs/CHAT.md](./docs/CHAT.md) "Multi-intent messages"). Also: **`tsx`-run dev processes (`npm run api`/`npm run worker`) do not hot-reload** — restart both after any backend source change before manually testing Chat, or you will observe stale behavior from the process's in-memory module graph, not the current code (see [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.1").

Phase 4D.2: Chat Action Layer + verified mutations + image/screenshot attachments — `ActionLayerService` (`src/application/action-layer.ts`) is now the only way Chat may mutate state (create/edit-title/start/cancel a task), reusing the existing `TaskService` mutation methods and always reading the task back from the database to verify the change actually happened before Chat may report success — the model's own claim is never treated as evidence (fixes a real reported incident where Chat claimed a status update that never happened). "Mark Done" and "retry/re-run" always honestly decline, since neither has a real domain transition (`REVIEW→DONE` only fires via merged-PR detection; `FAILED` is terminal) — never invented. Hedged/non-imperative language never mutates; an ambiguous task reference is refused and disambiguated, never guessed. Chat attachments also now accept PNG/JPEG/WEBP screenshots (real magic-byte validation, metadata-only persistence) — since no model/provider in this stack has a multimodal call path, Chat says so truthfully instead of fabricating an image analysis (see [docs/CHAT.md](./docs/CHAT.md) "Action Layer" / "Image/screenshot attachments").

Phase 4D.2.1: fixed a real browser-reported gap in action-language detection — a natural phrase like "make the review task add profile to done" used none of the words the original narrow `ACTION_MARK_DONE` pattern recognized, so the whole message fell through to the general free-text LLM path (which has no mutation capability) and it fabricated a false "I have updated the status..." claim while the real task stayed in Review. Fixed by broadening the action-verb patterns to cover natural completion phrasing (mark/make/set/move/close/complete a task done/completed/finished), adding a reverse fuzzy title match so a short reference resolves against a much longer real task title, and resolving "the oldest `<status>` task" as an action target via the same lookup the read path uses. Also added a code-level (not just prompt-level) scrubber on the free-text path itself: any first-person completed-mutation claim in its raw output is replaced with an honest refusal before reaching the user, since that path can never legitimately produce one. No new task-lifecycle transition was added — `markDone`/`retryTask` still always honestly decline (see [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.2.1").

Phase 4D.3: task management from general Chat — broadened natural-language reads ("which tasks need my input?", "show me the latest tasks", "what needs my attention?") and "oldest"/"first" task references for ACTIONS as well as reads ("start the oldest backlog task"), all routed through the existing Context/Action Layers, no new query or mutation mechanism. The one genuinely new capability is BULK mutations ("cancel all failed tasks", "start all backlog tasks"): these ALWAYS propose the exact target set first (`chat_conversations.pending_action_json`, migration 024) and execute only after an explicit confirming reply, looping the SAME single-task `ActionLayerService.cancelTask`/`startTask` per item with its own full read-back verification — never a bulk-specific domain operation, never an all-or-nothing transaction, so one task's legitimate failure never hides another's success. Single-task start/cancel/rename/create remain unchanged from Phase 4D.2 (direct execution on an unambiguous command) — confirmation was deliberately scoped to bulk mutations only, confirmed with the user rather than guessed, since the brief's own test list and acceptance criteria named confirmation as a bulk-only requirement and Phase 4D.2's single-task behavior was already shipped and tested. Also added idempotency for cancel (already-`CANCELLED` → "already Cancelled", no duplicate transition) and start (already-`TODO` → a clean message, not a raw state-machine error) (see [docs/CHAT.md](./docs/CHAT.md) "Task management from general Chat" and [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.3").

Phase 4D.3.1: fixed a real browser-reported parsing bug — a task titled with a bracketed bug-id list ("...(BUG-036, BUG-037)") combined with an action request ("...make this task from review to done") was split right at the comma INSIDE the parenthetical by the naive multi-intent clause splitter, breaking the title in half so neither fragment could resolve to the real task; the whole message surfaced as two garbled "I couldn't answer" fragments instead of one recognized action request. Fixed with a context-aware splitter (`splitRespectingNesting`) that tracks `(...)`/`[...]` nesting and `"..."`/`'...'` quote state and only treats a comma/"and" as a clause boundary outside all of them, plus masking for a bracket-less bug-id list ("BUG-036, BUG-037" bare). This was purely a parsing fix upstream of task resolution — once the clause survives intact it already resolves via the EXISTING exact-substring/fuzzy-match logic (Phase 4D.2/4D.2.1), and `ActionLayerService.markDone` already honestly declines a Review task exactly as before. No Task state machine change, no Review→Done transition (see [docs/CHAT.md](./docs/CHAT.md) "Comma/bracket/quote-aware clause splitting" and [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.3.1").

Phase 4D.3.2: diagnosed and fixed why the EXACT message live-verified in Phase 4D.3.1 still failed in the real browser, against the real pre-existing "Jinvani_OTT" project (32 tasks). Root cause, confirmed by querying the real production database directly and replaying the real resolution logic against it: `resolveActionTarget` fetched its candidate task list via the display-bounded `ContextLayerService.getTasks({ limit: 20 })` — correct for a user-facing list, but task-reference resolution never builds a model prompt at all, so bounding its search space silently made any task older than the 20 most recently created ones permanently unreferenceable by title or id. This is a completely independent bug from 4D.3.1's clause-splitting fix (confirmed: the clause itself stayed intact). Fixed by adding `ContextLayerService.getAllTasksForResolution` (unbounded, resolution-only, never used for display) and routing `resolveActionTarget` through it. Also ruled out, with direct evidence, a stale-process/port-collision explanation (an unrelated `eatro-backend` process was also bound to port 3000 on IPv4, but `localhost` resolves to the real CodeForge API's IPv6 listener first on this machine). Live-verified against the real project and real task with no credentials minted (see [docs/CHAT.md](./docs/CHAT.md) "Task management from general Chat" and [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.3.2").

Phase 4D.4: human-confirmed Review → Done completion from Chat — a SECOND, additional path to `DONE` alongside the existing, completely unchanged automatic PR-merge path. Before this phase, `Orchestrator.acceptReview(taskId)` already implemented exactly `REVIEW --accepted--> DONE` through the real state machine, but had zero callers anywhere in the codebase (dead code since whenever it was written) — this phase is what actually wires it up: `TaskService.completeTaskByHuman` → `Orchestrator.acceptReview` (now with an optional `provenance` parameter recording `completedBy`/`completedVia` on the `TASK_ACCEPTED`/`TASK_COMPLETED` events, backward compatible) → `ActionLayerService.completeTaskAsHuman`, gated behind the exact same propose→confirm→execute mechanism Phase 4D.3 built for bulk mutations (`ChatPendingAction` gained a `HUMAN_MARK_DONE` variant). Never mutates on the first message, no matter how explicit the wording; re-reads the task fresh at confirm time rather than trusting the status observed at proposal time, so a task that became `DONE` or moved elsewhere in the meantime (e.g. the PR merged automatically) is handled honestly, not blindly. No new `TaskStatus`, no new state-machine transition, no change to the automatic PR-merge path (see [docs/CHAT.md](./docs/CHAT.md) "Human-confirmed Review → Done completion" and [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.4").

Phase 4D.5: task discovery + conversational task references + real PR/merge status. Part A — natural-language task discovery ("Show me the Review task.", "Give me the review task.", "ready to start"/"currently running"/"waiting for me" status synonyms) through the existing Context Layer, with singular-vs-plural phrasing now distinguished. Part B — a lightweight structured conversational-referent pair (`lastTaskId` plus a new `lastTaskIds` ordered list, migration 025) replaces the single `lastTaskId` for ordinal ("the second one") and pronoun ("that task") references, resolved by one shared `resolveConversationalReference` function implementing an explicit 6-step priority chain (same-message mention → displayed-list ordinal → single-item-list → multi-item-list-with-pronoun → coarser `lastTaskId` fallback) that never lets a stale reference override a fresh query result, with reads and actions deliberately differing only in how readily they fall back to the coarsest, final step. Part C — `TaskService.getPullRequestStatus`/`ContextLayerService.getTaskPullRequestStatus` reuse the existing `SourceControlProvider` registry (no second GitHub client) to report real PR/merge state (no PR / OPEN / MERGED / CLOSED_NOT_MERGED / unavailable) as a domain kept structurally separate from `TaskStatus` — never conflated in either direction — plus review-age ("which task has been in Review the longest?") computed from the real `TASK_MOVED_TO_REVIEW` event history rather than `updatedAt`. Two real gaps were found and fixed by this phase's own test suite before any live verification: a "how many" question sharing a verb with an action trigger was misclassified as a command, and "give me the review task" phrasing fell through to the free-text LLM path — see [docs/CHAT.md](./docs/CHAT.md) "Task discovery + conversational task references + real PR/merge status" and [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.5".

Phase 4D.6: conversational context continuity + upload-aware Chat actions. Hardens the Phase 4D.5 conversational-referent chain across a full multi-turn chain (failed-list → oldest → "its" details → "what went wrong?" → "can it be retried?" all now consistently stay bound to the same task); confirms "oldest" was, and remains, real `createdAt` chronology and can never be read as BUG-ID numeric order (a regression test pins this down); grounds `TASK_FAILURE_REASON`/`TASK_RETRY_ELIGIBILITY` exclusively in persisted `TASK_FAILED`-event evidence or an honest "no recorded failure reason" — never a generic, invented domain-knowledge explanation; and gives an uploaded/imported bug sheet its own explicit, durable `chat_conversations.active_import_id` (migration 026) — a context deliberately separate from `lastTaskId`/`lastTaskIds` so task questions and upload questions never cross-contaminate. New deterministic upload intents (`UPLOAD_SUMMARY`/`UPLOAD_COUNT_ITEMS`/`UPLOAD_LIST_ITEMS`/`ACTION_UPLOAD_CREATE_TASKS_PREVIEW`) support natural-language dev-status filtering (case/whitespace/Unicode-dash-normalized, multi-status OR) read from already-persisted imported-row metadata — never a fresh model call for a deterministic filter — and task creation from a filtered selection always goes through the existing propose→confirm→execute mechanism into `ActionLayerService.createTask` (BACKLOG-only, never auto-started). No second import engine, no second task database, no second retry/mutation system — see [docs/CHAT.md](./docs/CHAT.md) "Conversational context continuity + upload-aware Chat actions" and [docs/PLATFORM_GAPS.md](./docs/PLATFORM_GAPS.md) "Phase 4D.6".

Multi-repository projects (TD-62): a project is created by name, then holds one repository (monorepo) or several (frontend/backend/admin…) via `project_repos` (migration 028, existing projects backfilled to one repository). Every task and backlog item targets exactly one repository; execution, branches, PRs, validation commands and analysis all run against the project *scoped to that repository* (`scopeProjectToRepo` / `ProjectRepository.findScoped`), so the orchestrator itself is unchanged. The repository is never guessed — several repositories and no choice is `REPOSITORY_REQUIRED`; Chat only uses a repository named in the message. Project Settings → Repositories manages them; see [docs/TECHNICAL_DECISIONS.md](./docs/TECHNICAL_DECISIONS.md) TD-62 and [docs/API.md](./docs/API.md).

Token usage (TD-63): every Chat reply, task outcome and backlog analysis shows roughly how many tokens it used (`src/usage/token-usage.ts` — reported input + output + reasoning, or a labelled ~4-chars-per-token estimate where CodeForge has the exchanged text; unreported task runs are flagged, never guessed). The Overview has a monthly project meter, Project Settings a project budget, Settings an account meter + budget (migration 029). Budgets only warn — work is never blocked.

Model Gateway: account-scoped, multi-provider AI configuration (Google/Anthropic/OpenAI) extending the pre-existing V1.1 Slice 5 routing machinery rather than replacing it — see [docs/MODEL_GATEWAY.md](./docs/MODEL_GATEWAY.md). `ModelGatewayService` (`src/application/model-gateway-service.ts`) resolves a per-account `ModelRegistry` built from encrypted `provider_connections` (migration 027, reusing the exact AES-256-GCM utility GitHub PATs already use) and a persisted Global AI Brain (`global_ai_configuration`: Auto or Fixed) through the UNCHANGED `selectModel`/`ProviderHealthRepository` — never a second routing policy. An account with zero connections behaves EXACTLY as before this feature (the pre-existing env-derived registry bridge); a Fixed brain naming a disconnected provider throws an actionable error rather than silently switching providers. `EngineInvocationRequest.credentialEnv` (additive, same posture as `modelSelection`) carries the resolved provider's decrypted key into `OpenCodeAdapter`'s sanitized child-process environment — never logged. The Orchestrator and `BacklogAnalyzer` (Chat's own call path) both resolve through the SAME gateway via a narrow `ModelGatewayLookup` interface (see [docs/TECHNICAL_DECISIONS.md](./docs/TECHNICAL_DECISIONS.md) TD-60 for why an interface, not the concrete class, to avoid inverting the Orchestrator's dependency direction). Settings → AI/Models gained real Connect/Test/Disconnect per provider and a Global AI Brain selector, replacing the prior read-only reporting view. Context Builder / model-neutral compaction were explicitly scoped OUT of this phase as their own, equally large follow-up (confirmed with the user before starting) — nothing here changes how much context any AI call receives. Live verification against real Google/Anthropic/OpenAI API keys has not been performed; all provider-adapter validation in tests uses a scripted adapter.

### Running this repo

Backend (repo root):
- `npm install`
- `npm run typecheck` — strict TypeScript, no emit
- `npm test` — Node's built-in test runner over `tests/*.test.ts`
- `npm run demo` — runs the full task lifecycle twice directly against the domain/orchestrator (no HTTP), against a disposable local git fixture repo: once showing the self-fix loop reaching `REVIEW`, once showing `NEEDS_INPUT` → human answer → `REVIEW`. Uses `FixtureCodingEngine`, not a live Claude Code CLI call — see the security-boundary note at the top of `src/coding-engine/claude-code-adapter.ts`.
- `npm run validate:backlog -- --project <id> --title … --description …` — Phase 4A.1 manual **real-provider** validation of backlog analysis (real OpenCode/model, on a database copy; refuses `CODING_ENGINE=fixture`) — see [docs/BACKLOG_INTELLIGENCE.md](./docs/BACKLOG_INTELLIGENCE.md) §11.
- `npm run validate:task-usage [-- --failure-scenario]` — Phase 4A.3/4A.4 **real-provider** usage reconciliation (raw OpenCode events vs persisted AgentRun vs task report; optionally a real timeout kill) on a throwaway fixture repo — see [docs/BACKLOG_INTELLIGENCE.md](./docs/BACKLOG_INTELLIGENCE.md) §4f.
- `npm run benchmark:retrieval -- --ground-truth <file> --repo <local git dir> [--variants a,b] [--investigation]` — deterministic file-selection benchmark (and premise-investigation replay) against your own ground truth (fix-touched vs adjudicated files, tune/hold-out split; data stays outside this repo) — §4e/§4g.
- `npm run validate:claim-verification -- --source-project <id> --repo-dir <path> --check-file <file>` — Phase 4A.5 **real** claim → approved check → executor → record → reconciliation chain (real model, a local clone at the analysed revision, DB copy) — see [docs/BACKLOG_INTELLIGENCE.md](./docs/BACKLOG_INTELLIGENCE.md) §4c.
- `npm run validate:bulk-backlog -- --source-project <id> --repo-dir <path> --csv <file> --source-name "…" [--check-file f]` — Phase 4B **real** import → bulk analysis → review report (real model, local clone, DB copy; approves/converts/starts nothing) — §4l.
- `npm run validate:adjudication -- --source-project <id> --repo-dir <path> --csv <file> --source-name "…" --seed <seed> [--apply filled.csv] [--keep-db <dir>]` — Phase 4B.1 **real** import → bulk analysis → deterministic sampling → human-fillable ground-truth template (never fabricates a label; `--apply` submits exactly what a human already wrote into the file) — §4m. Pass `--keep-db <dir>` to preserve the working database instead of deleting it at the end (the default without it is still destructive) — see §4q.
- `npm run validate:adjudication -- --resume <dir> [--apply filled.csv] [--project-id <id>] [--run-id <id>]` — Phase 4B.5 **real** re-open of a `--keep-db` directory in place: applies any filled CSV and re-freezes a baseline, without re-running real-model analysis — §4q.
- `npm run api` / `npm run worker` — the HTTP server and the background execution poller, as two separate processes (see [TECHNICAL_DECISIONS.md](./docs/TECHNICAL_DECISIONS.md) TD-16); `npm run dev` runs both together for local convenience. Set `CODING_ENGINE=fixture` to exercise them without a real Claude Code CLI/credentials. Full contract in [docs/API.md](./docs/API.md). Every request now needs a session — `curl` against a protected route without first `POST`ing to `/auth/register` or `/auth/login` (and reusing the returned cookie) gets a `401`.
