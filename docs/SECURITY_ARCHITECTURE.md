# Security Architecture

The platform executes AI-driven code changes against real repositories and, eventually, real deployment targets. Security is a first-class concern from MVP, not a later hardening pass — retrofitting isolation and credential scoping into a system that started without them is far more expensive than designing for it now.

## Threat surface

- Untrusted/uncertain LLM output executing shell commands and editing files.
- Credentials for source control and (later) deployment/cloud.
- Multi-project, eventually multi-tenant, data and secret isolation.
- A human-in-the-loop UI that can trigger real, hard-to-reverse actions (push, PR, deploy).

## Principles

1. **No raw credentials in prompts, logs, or source files.** Credentials are injected into the execution environment (env vars / mounted short-lived files) by the Workspace provisioning step, never included in any text sent to a coding engine or persisted in the task record/event log.
2. **Least privilege, scoped, short-lived.** A workspace receives only a credential scoped to the one repository the task targets, with an expiry tied to the task's execution window — not a broad personal-access token reused across tasks.
3. **Sandboxed execution.** Every task runs in an isolated, ephemeral container: no access to other tasks' workspaces, other projects' credentials, or the host beyond what the project's declared build/test environment requires.
4. **Command execution restrictions.** The execution environment applies a constrained policy (resource limits; network access limited to what the project's build/test/dependency-install step needs) rather than unrestricted host access.
5. **Deployment requires explicit human approval.** No gate pass ever triggers a deployment automatically — a human action in the UI is required before the Deployment abstraction is invoked (see [INTEGRATION_ARCHITECTURE.md](./INTEGRATION_ARCHITECTURE.md)).
6. **Audit everything.** Every state transition, gate result, and agent action is recorded in the append-only task event log (see [ARCHITECTURE.md](./ARCHITECTURE.md#16-observability--audit)) — who/what triggered a change is always reconstructable.
7. **Project isolation now, tenant isolation ready.** MVP runs single-tenant, but `tenant_id` is present on every relevant table and every workspace/credential scoping decision is made at the project level — so tenant-level isolation is a policy change, not a schema migration, when multi-tenant ships.

## Secrets management

- **What's stored**: a *reference* (e.g. a secret-manager path/ID) in the platform database — never the secret value itself.
- **What's issued at runtime**: the Workspace provisioning step resolves the reference against a secrets manager and injects a scoped, short-lived credential directly into the container for that task's duration only.
- **MVP**: a single, operator-managed secrets store (e.g. a managed secrets manager or, for pure local dev, an encrypted local store) — the interface is what matters, so this is swappable later without touching how credentials are consumed by the Workspace layer.
- **Never**: secrets committed to project repos, embedded in project context files, or written into task records/reports.
- **Implemented (Step 7 & 8A) — GitHub credentials & Engine Sanitization**: the first concrete secret type stored by the platform. AES-256-GCM at rest (`src/auth/credential-encryption.ts`), key from `CREDENTIAL_ENCRYPTION_KEY` (env, resolved lazily), one credential per user. Injected into the platform's own `git clone`/`push` child processes only, as ephemeral environment variables (`GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`) — never written to `.git/config` (which the coding engine can read), never a CLI flag (visible via `ps aux`), never embedded in a clone URL. Coding engine adapters (`OpenCodeAdapter`, `ClaudeCodeAdapter`) sanitize their child process environments to ensure `CREDENTIAL_ENCRYPTION_KEY`, `GITHUB_TOKEN`, and platform secrets never enter the coding agent. Full design in [GITHUB_INTEGRATION.md](./GITHUB_INTEGRATION.md) and [CODING_ENGINE.md](./CODING_ENGINE.md).

## Isolation model

- **Per-task workspace**: fresh clone/worktree, dedicated branch, dedicated container, torn down after the task's step completes or the task reaches a terminal/paused state.
- **Per-project boundary**: a project's credentials, context files, and workspace are never accessible from another project's task execution, even when tasks run concurrently on the same worker pool.
- **Per-tenant boundary (future)**: same mechanism, one level up — workspaces, secrets, and data queries are always scoped by `tenant_id` once multi-tenant is enabled.
- **ProjectWorkspace file operations (Phase 3, Slice 4)**: `ProjectWorkspaceFsManager` (`src/project-workspace/project-workspace-fs-manager.ts`) is the sole path by which any code reads/writes/lists inside a persistent ProjectWorkspace directory. Two independent safety layers, both enforced unconditionally (not just when a request "looks" untrusted): (1) lexical validation rejects absolute paths, `..` traversal, and Windows-style paths before a caller-supplied relative path ever reaches `path.resolve`, plus a resolved-path containment check against the ProjectWorkspace directory; (2) a real, symlink-aware containment check (`assertNoSymlinksInPath`) additionally rejects *any* symlink found anywhere along a resolved path — chosen specifically because lexical validation alone cannot detect a symlink physically placed inside a ProjectWorkspace pointing outside it (e.g. `safe-link -> /etc`), where the path string itself looks perfectly safe. No authorization logic lives in this class — `ProjectService`, behind `assertProjectAccess`, is responsible for confirming the caller may act on a given ProjectWorkspace before ever reaching it. This slice deliberately adds no HTTP endpoints (see [API.md](./API.md)); it exists as the safe internal primitive future project-context/RAG/MCP/AI-chat features will build on.
- **Project Context Manifest ≠ security policy (Phase 3, Slices 5-7)**: `ProjectContextService` (`src/project-workspace/project-context-service.ts`) reads/writes a single, schema-validated JSON file (`.project-context.json`) inside a ProjectWorkspace via `ProjectWorkspaceFsManager` — never a direct filesystem call, and never a caller-controlled relative path (the filename is a fixed constant). This manifest is project-owned, human-authored **data** — instructions, architecture notes, conventions, validation guidance, constraints — never a source of authorization or a replacement for any application guardrail. Nothing in it can alter ownership, permissions, GitHub credentials, filesystem roots, task lifecycle, or orchestrator state transitions; an instruction written inside it (e.g. "ignore authorization", "auto-merge this PR", "increase retry limits") has zero effect on backend behavior, precisely because no code path ever interprets manifest content as anything other than inert text to store, bound, and pass through. `ProjectWorkspace filesystem` (this persistent, project-scoped directory) also remains categorically distinct from the existing, ephemeral, per-task execution `Workspace` (`src/workspace/*`) — the manifest lives exclusively in the former.
  - **Slice 6 — AI task execution**: the manifest IS now injected into Implementer/Reviewer prompts (`orchestrator/project-context-loader.ts` -> `orchestrator/project-context-section.ts` -> `ContextBundle.projectContext`), always as a clearly-delimited "PROJECT CONTEXT" section whose own text states it is project-provided guidance that never overrides system/developer/security/orchestration instructions and is never a command to execute. Deterministically bounded (`MAX_PROJECT_CONTEXT_SECTION_CHARS`, independent of the manifest's own much larger 256 KiB storage limit) — truncated only at whole-line boundaries, never mid-instruction, with an explicit omission notice, so project context can never cause unbounded prompt growth. `validation.commands` inside the manifest is guidance text only, never executed as a shell command — `Project.commands` (the existing, DB-authoritative, executable build/test/lint configuration) is unchanged and remains the only thing the orchestrator actually runs. Loading degrades gracefully (missing ProjectWorkspace, missing manifest, or a corrupt on-disk manifest all resolve to `null` — never a thrown error) so a task never fails merely because project context couldn't be loaded. See `tests/project-context-ai-integration.test.ts` for adversarial-manifest-content tests proving retry limits, reviewer verdicts, and branch selection all remain governed solely by the orchestrator's own configuration and logic.
  - **Slice 7 — revision/versioning is platform bookkeeping, not project data or an AI instruction**: the manifest's `revision` field (optimistic-concurrency counter — see `project-context-manifest.ts`'s "VERSION vs. REVISION" doc comment) is written and interpreted exclusively by `ProjectContextService`/the `PUT` route; nothing about it is project-authored, and it is deliberately never rendered into the AI-facing section from Slice 6 (`renderProjectContextSection` only reads the specific content fields, never `revision` — see `tests/project-context-versioning.test.ts`). **Concurrency mechanism**: `ProjectWorkspaceFsManager.withExclusiveLock` (`open(path, "wx")`, i.e. `O_CREAT|O_EXCL` — a single atomic syscall, not a read-then-write this code could race on) serializes the read-current → compare-revision → construct-next → write sequence per ProjectWorkspace, so a stale `PUT` is rejected (`409 PROJECT_CONTEXT_CONFLICT`) rather than silently overwriting a newer revision — see `ProjectContextService.replaceManifest`'s own doc comment for the exact sequence and the race it closes. **Honest limitation**: `O_EXCL`'s cross-process atomicity is a real POSIX-local-filesystem guarantee (holds across every OS process sharing that disk, including this platform's documented single-host API+worker deployment — see [DEPLOYMENT.md](./DEPLOYMENT.md)), but is NOT re-verified against network filesystems (NFS has a long-documented history of unreliable `O_EXCL` semantics across clients) — if `PROJECT_WORKSPACE_ROOT` is ever moved onto shared network storage, this guarantee needs re-verification against that filesystem's actual semantics before being relied on. No stronger claim is made than what the local-filesystem primitive actually provides.
  - **Project context is data, not policy — git operations are platform-owned and take precedence (V1.1 Slice 1)**: a connected project's own instructions to a human developer ("always create a feature branch", "commit as you go") are exactly the kind of manifest content described above — data to inform the Implementer, never a policy this platform follows. Before this slice, nothing enforced that distinction for git specifically: a real task's project context told the agent to branch, the agent ran its own `git checkout -b`, and every platform-owned step downstream (commit, push, review, PR) kept reporting success against the wrong branch (see [PLATFORM_GAPS.md](./PLATFORM_GAPS.md) GAP-015). Two independent layers now enforce this rather than relying on the model reading a disclaimer correctly: (1) `buildImplementerPrompt` (`src/coding-engine/prompt-builder.ts`) explicitly instructs the agent never to run `git branch`/`checkout`/`commit`/`push`, states that any such instruction elsewhere in the prompt — including in the project's own context — does not apply, and that this line overrides it; (2) independent of whether the model complies, `git-commit.ts`'s `assertOnExpectedBranch` is the actual enforcement — called before every platform-owned commit and push, it throws `BranchMismatchError` and refuses to touch git history or the remote if the workspace is not on the branch the platform recorded for the task. The prompt instruction is a preference; the branch assertion is what makes violating it harmless.

## AI claims are not execution evidence (V1.1 Slice 1)

A coding engine's own summary of what it did — "tests passed," "I verified the regex," "changed 3 files" — is a claim about its own work, produced by the same process whose work is being evaluated. It must never become the platform's own record of what happened. See [PLATFORM_GAPS.md](./PLATFORM_GAPS.md) GAP-016 (a reviewer described, in detail, how a regex correctly rejected bad input; that exact regex, run against that exact input, let it through) and GAP-024 (three task summaries in one batch quoted command output and diffs that never happened) for the real incidents this principle was written in response to.

Concretely, three places in the execution loop now draw a hard line between the two:

- **Files changed**: `TaskReport.filesChanged` and the PR's "Files changed" section are computed from `git status --porcelain`, captured by `commitAllLocal` (`src/source-control/git-commit.ts`) *before* anything is staged — never from `StepResult.filesChanged`, which is derived from the coding engine's own tool-call log (a claim about what it believes it touched). `CommitResult.changedFiles` is the platform's own git evidence; `StepResult.filesChanged` remains in the type only because the engine adapter layer still produces it as part of the AI's summary, and it is deliberately not read by anything that presents itself as evidence.
- **Validation outcome**: `CheckResult`/`ValidationResult` gained an `outcome` field (`CheckOutcome`/`ValidationOutcome` — see `domain/types.ts`) that can only ever be set by `validation-runner.ts` from a command the platform itself spawned and watched exit — an AI's own claim about whether its fix works has no path into this field at all. The same field is what distinguishes "no commands were configured" from "the configured commands genuinely passed" (GAP-004) and "timed out" from "genuinely failed" (GAP-002), rather than collapsing all three into a bare `passed: false` a self-fix loop or a human would otherwise read as "there's a bug in the diff."
- **Review verification language**: `ReviewResult.verificationMethod` (`"static" | "executed" | "unknown"`) is parsed from an explicit `VERIFICATION:` line the reviewer prompt requires, and the prompt separately forbids the words "verified"/"confirmed"/"independently verified" unless the reviewer actually ran something and is reporting its real output. The PR description and task report always show this label — including `"unknown"`, when the model never said which one it did — so a static read-through is never presented to whoever merges the PR as more than it was.

What this did **not** yet do (closed by V1.1 Slice 2 below, except where noted): nothing in Slice 1 gave the Reviewer a platform-mediated way to actually execute a check and have that output captured as evidence — a reviewer that said `VERIFICATION: EXECUTED` was still trusted to be telling the truth about what it ran and what it saw. `TaskRecord.bugFixVerification` remains an inert extension point for a future task type (reproduce → implement → platform-executed post-fix verification) — see [PLATFORM_GAPS.md](./PLATFORM_GAPS.md) GAP-016 and GAP-023.

## AI may request verification. CodeForge owns verification evidence. (V1.1 Slice 2)

Slice 1 made the platform's *own* evidence (files changed, validation outcome, verification language) trustworthy. It left one gap open by design: the Reviewer's claim to have executed something was still just a claim — nothing made "EXECUTED" mean anything more than "the model wrote that word." This slice closes that gap without giving the Reviewer any new execution privileges of its own.

**The mechanism**: the Reviewer may respond with a bounded `VERIFY: <checkId>` line (`review/reviewer.ts`'s `parseVerificationRequest`) naming one of the project's own already-configured build/test/lint/typecheck commands — never an arbitrary shell command, never a working directory it chooses, never a command it invents. `review/reviewer-verification.ts`'s `executeApprovedVerification` is the only thing that acts on this request: it checks the id against `Project.commands` (an unknown or unconfigured id is rejected before anything is spawned — `outcome: "rejected"`, no process ever created), and for an approved id it runs the exact same `runCheck` (`validation/validation-runner.ts`) the Implementer's own declared checks already use — no second execution engine, no new spawn/timeout/cancellation logic. The result (`VerificationEvidence`: outcome, exit code, duration, captured stdout/stderr, the real branch/commit the check ran against) is handed back to the Reviewer in a follow-up prompt, and the Reviewer gives its actual verdict from there.

**The trust boundary this closes**: `review/reviewer.ts`'s `deriveReviewResult` now computes `ReviewResult.verificationMethod` as `"executed"` **only** when real `VerificationEvidence` with a non-`"rejected"` outcome exists — a Reviewer that writes `VERIFICATION: EXECUTED` with nothing behind it is downgraded to `"static"`, regardless of how confidently the prose reads. This is the direct fix for the GAP-016 incident: the model's own account of what it ran is no longer sufficient to mark anything "executed" — only the platform's own spawned process can.

**Commit binding**: `VerificationEvidence.commitSha`/`actualBranch` are captured live from the workspace immediately before running the check, and evidence is never carried across a review cycle — an Implementer fix after a rejection produces a new commit and a fresh (or absent) verification for the next cycle, so evidence for a stale commit can never be presented as proof for a new one.

**What this still does not do**: the bound is exactly one verification round trip per review attempt — a Reviewer cannot chain multiple checks in one cycle, only request `build`/`test`/`lint`/`typecheck` (never a project-specific script outside those four slots), and cannot execute anything on its own initiative outside this one platform-mediated path. See [PLATFORM_GAPS.md](./PLATFORM_GAPS.md) GAP-016's closing note for the exact scope this closed versus what remains.

## AI may describe/interpret. CodeForge owns verification policy, execution, evidence, and status. (V1.1 Slice 3)

Slice 2 gave the Reviewer a trustworthy way to request one platform-executed check mid-review. This slice reuses the exact same execution mechanism (`executeApprovedVerification` — no third execution engine) to make `TaskRecord.bugFixVerification` (an inert placeholder since Slice 1) a real, working reproduce → implement → verify loop, orchestrator-owned end to end.

**The contract**: a task may be created with a `BugFixVerificationContract` (`domain/types.ts`) — a `checkId` (one of the project's own configured build/test/lint/typecheck commands, exactly the same vocabulary Slice 2's `VERIFY:` protocol uses) plus `bugPresentWhenCheckOutcome` (`"failed"` or `"passed"`), an explicit, typed field that decides what "the bug is present" means for that specific check — never an arbitrary command, and never a judgment an LLM makes. Set once at task creation (`task-factory.ts`'s `CreateTaskInput.bugFixVerification`); immutable thereafter.

**The flow, entirely orchestrator-driven** (`orchestrator.ts`'s `runWorkingEpisode`, `runBugReproduction`/`runFixVerification`): before the Implementer's first invocation, the platform runs the contract's check against the workspace's pristine starting commit and derives a deterministic `ReproductionStatus` (`review/bug-fix-verification.ts`'s `deriveReproductionStatus` — pure data, a lookup against the contract's own field, never inferred). After every commit that follows (the first, and every review/fix-cycle recommit), the platform re-runs the identical check against the new commit and derives a `FixVerificationStatus` the same deterministic way, **overwriting** the task's own record with the fresh result — the previous commit's evidence is never left presentable as evidence for a newer commit (see `tests/bug-fix-verification-integration.test.ts` scenario H/I, which proves two real, distinct commits each get their own, non-stale evidence).

**Reviewer prose cannot manufacture or override this**: the Implementer and Reviewer both receive this evidence in their prompts, explicitly labeled "PLATFORM-CAPTURED... not an AI claim" (`coding-engine/prompt-builder.ts`), but nothing either of them writes ever flows back into `TaskRecord.bugFixVerification` — only the orchestrator's own `runBugReproduction`/`runFixVerification` ever write to it, from real evidence. A Reviewer that approves a change while claiming "the fix is verified" does not change a recorded `fix_not_verified` (`tests/bug-fix-verification-integration.test.ts` scenario J/K) — the Reviewer's verdict (a legitimate, separate code-quality judgment) and the platform's own verification status can disagree, and the platform's own record is what a report/PR shows as authoritative.

**Crash safety reuses existing infrastructure, not a new one**: both `runBugReproduction` and `runFixVerification` follow the same idempotent-write pattern every other step in `runWorkingEpisode` already uses (`WORKSPACE_CREATED`, `COMMIT_CREATED`, etc.) — nothing is persisted to `TaskRecord.bugFixVerification` until the real check has actually completed, so an interruption before that point simply leaves the field `null` for the next resume to fill in fresh; nothing here can turn a crash into a false `FIX_VERIFIED`.

**What this does NOT do**: this is opt-in and reachable today only through `TaskService.create`'s `CreateTaskInput.bugFixVerification` — no HTTP endpoint or Create Task UI field exists for it yet, so it is not the automatic experience for an ordinary bug-report task. The human-review-feedback fix loop (a task already in REVIEW, a human requesting changes on GitHub) does not re-run fix verification — this slice's scope is the original implement/review loop only. See [PLATFORM_GAPS.md](./PLATFORM_GAPS.md) GAP-016's Slice 3 note for the full accounting.

## AI can make claims about why it failed. CodeForge decides what's worth retrying. (V1.1 Slice 4)

Real-world use (see PLATFORM_GAPS.md GAP-027/GAP-028) surfaced the platform's biggest single trust gap so far: it could not tell a genuine task/code failure apart from a transient infrastructure one — a provider quota limit, a timed-out invocation, a dropped `git clone` — and treated all of them identically as permanent, terminal `TASK_FAILED`. A provider outage that would have resolved itself in minutes instead destroyed an entire queued backlog, one task at a time.

**The taxonomy**: `orchestrator/failure-classifier.ts`'s `classifyOrchestratorFailure` is the single, structured decision point — never `error.message.includes(...)` scattered through the codebase. It reuses every existing structured classifier rather than inventing a fourth (`EngineExecutionError.meta`, itself built by the pre-existing `coding-engine/engine-failure-classifier.ts`; `integrations/github/error-classifier.ts`'s `classifyGitHubError`), and is conservative by construction: an error it cannot positively identify as infrastructure-related — no known type, no GitHub typing, no phase hint confirming it happened during a workspace/commit/push/PR call — defaults to `unknown_failure`, **not retryable**. This matters concretely: a genuinely unexpected exception (a real bug) must never be blindly retried just because *some* errors from *some* code paths are; only errors this function can actually justify as transient ever are.

**Retryability is never the AI's to decide.** A coding engine's own explanation of why it failed is exactly the kind of claim Slice 1 already established the platform must not take at face value — the model never gets a vote on whether or how many times to retry. The decision is made entirely by `classifyOrchestratorFailure`'s output (`{ category, retryable, reason, retryAfterMs }`) and the orchestrator's own bounded policy (`OrchestratorConfig.maxInfrastructureRetries`/`maxInfraCheckRetries`, conservative defaults).

**Resumability is reused, not rebuilt.** `Orchestrator.runEpisodeWithInfrastructureRetry` wraps the whole `runWorkingEpisode`/`runHumanFeedbackFixCycle` call: on a retryable failure it waits (bounded exponential backoff + jitter — `coding-engine/retry-backoff.ts`, the same primitive `OpenCodeAdapter`/`GitHubClient` already use — taking the larger of the computed delay and any provider/GitHub-suggested `retryAfterMs`) and calls the SAME function again. That re-entry lands back at the last safe boundary only because the step itself is already idempotent (a `ready` workspace is reused rather than re-cloned; `commitAllLocal` is a no-op when nothing changed; `ensurePullRequest` searches before creating) — the exact same properties crash recovery already depended on. No second resume mechanism was introduced.

**Crash recovery and infrastructure recovery are deliberately distinct, sharing only lease-fencing.** A crash means the worker process itself disappeared — nothing catches or classifies anything, and the existing lease/heartbeat/orphan-detection machinery (unmodified by this slice) is what lets a second process resume. Infrastructure recovery means the *current, still-alive* process's own operation failed for a transient reason — this slice's whole contribution. Both call `assertStillOwned` before resuming meaningful work, so a takeover mid-backoff is caught the same way either path already guards against it (see `tests/infrastructure-retry.test.ts` tests K/L/M/N: cancellation, lease loss, a genuinely abandoned/crashed process, and two workers racing the same retry all behave correctly).

**Nothing here weakens an existing boundary.** Retry never re-claims a task for a different project or workspace, never re-authorizes anything, never bypasses `assertOnExpectedBranch`/branch integrity, never re-executes a commit/push/PR step outside the same idempotency guards those steps already had before this slice, and the retried step still runs inside the exact same isolated task workspace.

**What this slice deliberately does NOT do** (see PLATFORM_GAPS.md GAP-027/028's own "Still open" notes and this slice's own scope boundary): no model/provider fallback or routing — a retried attempt uses the exact same engine/model configuration, every time; no cross-task circuit breaker — each task still independently discovers and retries a provider-wide outage rather than the worker recognizing the pattern once; no manual "retry" action once the bounded budget is genuinely exhausted. All three are explicitly left for a future slice to build on top of the structured failure taxonomy this one establishes.

## CodeForge owns routing. The model never chooses itself. (V1.1 Slice 5)

Real-world use exposed the platform's coupling to a single AI provider as a business risk, not just a reliability one (see PLATFORM_GAPS.md GAP-027/028's own "Still open" cross-task-outage note): a Gemini quota limit stops otherwise-valid work, with no architectural path to a second provider without rewriting the orchestrator. This slice builds that path — a provider/model routing layer the orchestrator owns, never the AI.

**The abstraction**: `routing/model-registry.ts`'s `ModelRegistry` is a configurable catalog of `ModelProfile` entries (modelId, providerId, which registered `CodingEngine` key executes it, a qualitative capability profile, `enabled`) — a new model/provider is a data registration, never an orchestrator code change. Production wiring (`env-platform.ts`'s `buildModelRegistryFromEnv`) registers exactly ONE profile, derived from `OPENCODE_MODEL` — the one model this environment can actually execute today; when `OPENCODE_MODEL` is unset, the registry stays empty and nothing routes, preserving the exact pre-Slice-5 behavior (the coding engine falls back to its own construction-time default). No fake `FakeOpenAIProvider`/`FakeClaudeProvider` exists anywhere in production code — see this slice's brief, item 25 — the only place multiple profiles are ever registered is a test's own `ModelRegistry` instance, a legitimate test double at the provider-abstraction boundary, never a claim that a second provider is executable.

**The routing decision**: `routing/model-router.ts`'s `selectModel` is a pure, deterministic function of (registry contents, persisted provider health, operation, engine key) — same inputs always produce the same candidate. It never compares a fabricated numeric "intelligence score" between models (see `ModelCapabilityProfile`'s own doc comment: capability is qualitative, `"unknown"` by honest default, never guessed). `Orchestrator.runAgent` calls it once per Implementer/Reviewer invocation and persists the result (`AgentRun.modelId`/`providerId`/`fallbackIndex`) — this is the ONLY place a model gets selected; the AI itself never sees or influences this decision.

**Provider health / cross-task outage protection**: `provider_health` (new table, migrations/012_model_routing.sql) persists one row per `providerId` — deliberately NOT in-memory, because an in-memory circuit breaker would be invisible to a second worker process or a later task entirely (this slice's brief, items 13/14). Every retryable infrastructure failure (reusing Slice 4's own `classifyOrchestratorFailure` — no second failure classifier was built) immediately cools that provider down for a bounded window (`routing/provider-health-policy.ts`); a real success clears it. This is the SAME mechanism that prevents one execution from repeatedly re-selecting a model whose provider just failed (loop prevention) and lets a later task, even from a different worker, see that a provider was recently unhealthy — one persisted fact, two consumers.

**Fallback reuses Slice 4's own retry layer, not a new one**: a model/provider fallback is not a separate loop bolted onto `runAgent` — an engine failure that Slice 4's `classifyOrchestratorFailure` marks retryable already triggers `runEpisodeWithInfrastructureRetry`'s existing bounded backoff-and-retry; because `runAgent`'s own provider-health recording happens BEFORE that retry re-enters, the retried attempt's `selectModel` call naturally sees the just-failed provider in cooldown and picks a different eligible candidate if one exists. One retry mechanism, model-aware by construction, not two.

**Evidence guarantees are untouched by which model ran**: branch integrity (`assertOnExpectedBranch`), workspace isolation, the validation runner, reviewer verification (Slice 2), bug-fix verification (Slice 3), and commit/push/PR integrity (Slice 1) are all enforced entirely independently of which model produced the diff — nothing in the routing layer has, or needs, any special access to bypass them. A fallback model's implementation goes through the identical validate → review → verify pipeline the original model's would have.

**Security boundaries preserved**: `ModelProfile` carries no credential material at all (`credentialMode` is a label — `"managed"` or `"byok"` — never a secret value; see this slice's own test coverage, `tests/model-routing-integration.test.ts` test P) — provider API keys remain exactly where Slice 1's "Secrets management" section already puts every other credential: server-side, injected at execution time, never in a prompt/report/log/event. Model selection depends only on the project's own `codingEngine` key and provider health — never on `projectId`, so there is no code path by which one project's routing could be influenced by another's configuration (no per-project credential store for AI providers exists yet — see "What this does NOT do" below).

**What this slice deliberately does NOT do**: no billing, no subscriptions, no usage limits or overage enforcement (usage telemetry — `AgentRun.cost`, already-existing `CostMetadata` — is captured for future pricing decisions, never acted on here); no BYOK credential storage or resolution end-to-end (the `ProviderCredentialMode` domain distinction exists, nothing implements per-project provider-credential storage yet); no second real, executable provider (only what `OPENCODE_MODEL` names); no complexity/risk-based model selection (routing is operation-aware only — see `OperationClass` — a real complexity signal is future work, deliberately not approximated here per this slice's own brief, item 9, which explicitly warns against an unreliable complexity score).

## Authentication & Authorization

**Implemented (Step 6)** — see [AUTHENTICATION.md](./AUTHENTICATION.md) for the full design. Summary: server-side sessions (opaque token, HttpOnly `SameSite=Lax` cookie, no JWT, no client-side secret storage), `crypto.scrypt` password hashing, and ownership-based authorization (`User -> owns -> Project -> tasks`) enforced in the application layer on every request — never left to the frontend. Every project/task access check returns `404`, not `403`, for a resource that exists but isn't the caller's, so the API never confirms existence to an unauthorized caller.

- **Deployment approval** and any future "risky action" (e.g. merging, force-pushing) are treated as privileged actions distinct from ordinary task creation — eligible for stricter checks later (e.g. requiring a specific role) without redesigning the auth model, because authorization is already action-scoped, not just project-scoped.

## Multi-user isolation audit (hosted multi-user MVP milestone)

Before this platform is reachable by more than one real developer over the public internet (the goal of the hosted-MVP milestone this section documents — see [DEPLOYMENT.md](./DEPLOYMENT.md)), every cross-user data-leak vector named in that milestone's brief was traced through the actual code (not assumed from the existing test suite's docstrings) and independently re-verified. This extends, rather than repeats, TD-46's earlier audit (`docs/TECHNICAL_DECISIONS.md`) — TD-46 covered the original Step 6 authentication/authorization surface; this pass specifically covers projects/tasks/task-events/reports, GitHub credentials, and workspace directories together, as one milestone's explicit deliverable.

**Verdict: no gap found.** Every code path was traced to its actual authorization/scoping check, not inferred from a comment claiming one exists.

1. **Project/task/event/report access.** Every route in `src/api/routes/{projects,tasks,integrations}.ts` is mounted behind `requireAuth` at the router level (`src/api/app.ts`), so a new route is protected by default rather than by remembering to add a check. Every service method that reads or mutates a project or task (`ProjectService`, `TaskService`, `HumanInputService`) calls `assertProjectAccess`/`assertTaskAccess` (`src/application/authorization.ts`) before touching a repository — including `TaskService.getReport` (task events, execution history, `failureContext`) and `TaskService.checkReviewFeedback`, both audited specifically since they were added after the original Step 6 test suite. `TaskRepository.findById`/`ProjectRepository.findById` are themselves unscoped (primary-key lookups with no owner filter) — that's fine only because every HTTP-reachable caller goes through the `assertProjectAccess`/`assertTaskAccess` choke point immediately after fetching, before anything reaches a response; no request handler or reachable service method calls either `findById` directly. **Noted as a footgun for future work, not a current vulnerability**: these two repository methods are reusable primitives with no compiler-enforced guard — a future route or script that called them directly instead of going through the choke point would leak cross-user data. Nothing in this codebase currently does that; a lint rule or review checklist item is the natural way to make that mistake structurally harder to make, not built here since there is no actual instance of it to fix.
2. **GitHub credential access.** `GitHubIntegrationService.connect/getStatus/disconnect` and `GitHubCredentialRepository.findByUserId` are keyed exclusively by `userId`, sourced only from `req.user!.id` (the session-derived identity) in `src/api/routes/integrations.ts` — never from a request body, query param, or header. Mid-task credential resolution (`resolveGitHubToken`, called from `GitHubSourceControlProvider`) is keyed by `project.ownerId` — a server-derived, immutable field set once at project creation from the creator's own session — never by any client-suppliable id. No route or code path resolves a GitHub credential by an id a caller controls.
3. **Workspace isolation.** `LocalGitWorkspaceProvider.provision` (`src/workspace/local-git-workspace-provider.ts`) derives every workspace's filesystem path as `join(WORKSPACES_ROOT, task.id)`, where `task.id` is a `randomUUID()` assigned once at task creation (`src/orchestrator/task-factory.ts`) — never derived from a project name, GitHub `owner`/`repo`, or any other user-supplied string. `owner`/`repo` only ever flow into `repoUrl` and into `git clone`/`git checkout` arguments (via `execFile`, never a shell — no shell-injection vector), never into a `path.join` call — so an adversarial `owner`/`repo` value (path-traversal segments, shell metacharacters) cannot make the workspace directory itself resolve outside `<WORKSPACES_ROOT>/<taskId>`. **Verified directly, not just by code reading**: `tests/workspace-isolation.test.ts` (added this milestone) runs two different users' tasks — one with a deliberately adversarial `owner: "../../etc"`, `repo: "passwd; rm -rf /"` — through the real orchestrator and provider against a shared `WORKSPACES_ROOT`, and asserts both workspace paths are exactly `<root>/<taskId>`, never collide, and never contain each other's task directory.
4. **Existing test coverage re-verified, not assumed.** `tests/auth.test.ts` and `tests/github-integration.test.ts` were read in full (not just their test names) to confirm each cross-user scenario the docs claim is actually asserted against a real second authenticated user and a real HTTP response — `404` on cross-user project/task/report/events access, `401` across the full unauthenticated-request sweep, header-based impersonation rejected, and fully isolated GitHub connections (`connect`/`status`/`disconnect` for user A never visible to or affected by user B). No gap between documented and actually-tested behavior was found.

**Why no code changes were needed here**: the audit confirmed the existing `assertProjectAccess`/`assertTaskAccess` choke point (already the subject of TD-32, TD-34, TD-46) and the `taskId`-only workspace path derivation already satisfy every isolation property this milestone's brief asks to verify. One new test file (`tests/workspace-isolation.test.ts`) was added specifically because workspace-path collision/escape was a property the existing suite implied but never asserted against the real provider — everything else already had direct test coverage.

## GitHub credential model — current state and limitations

The concrete implementation behind "Secrets management" above, for the one secret type this platform actually stores today (see [GITHUB_INTEGRATION.md](./GITHUB_INTEGRATION.md) for the full design): a Personal Access Token, one per user, AES-256-GCM encrypted at rest under `CREDENTIAL_ENCRYPTION_KEY`. This is a deliberate, explicit tradeoff (TD-36), not an oversight — a GitHub App (fine-grained, centrally revocable, repo-scoped installation tokens) is the architecturally preferred mechanism for a production multi-tenant product, but requires registering a GitHub App and hosting a public OAuth/installation callback URL, neither of which this MVP's single-operator-run deployment story has. **This milestone's brief explicitly keeps the PAT model rather than replacing it** — the limitations below are documented, not solved:

- **Scope**: whatever the user granted the token at creation time (ideally `repo`-only) — the platform cannot narrow it further.
- **Revocation is two-sided**: `DELETE /integrations/github` deletes only the platform's stored copy; the user must separately revoke/rotate the token on GitHub's own side to fully cut off access. The platform holds no more authority over the token's lifecycle than any other holder of it.
- **`CREDENTIAL_ENCRYPTION_KEY` is a single point of failure for every stored token**: losing it makes every previously-connected PAT permanently undecryptable (authenticated encryption — AES-256-GCM — means there's no partial-recovery path). See [DEPLOYMENT.md](./DEPLOYMENT.md) "Secrets configuration in production" for the operational guidance (generate once on the host, back it up completely separately from database backups, never commit it).
- **No rotation tooling**: rotating the key requires re-encrypting every stored credential row; not automated. The documented manual path is a full reconnect (each user re-supplies their PAT) after the key changes.
- **One credential per user, not per project**: every GitHub project a user connects uses the same token — narrower per-project credential scoping isn't available with a PAT (a GitHub App's installation-token model would give this for free, which is exactly why it's the preferred long-term mechanism per TD-36).

Swapping in a GitHub App later requires no change to `SourceControlProvider`, `Orchestrator`, or any core logic — only a new provider registered under the same interface (TD-37) — so none of the above is a design dead-end, just an accepted MVP-scope tradeoff.

## What's explicitly deferred (and why that's safe)

- Fine-grained RBAC beyond project membership — not needed with one role (developer) in MVP; the authorization boundary is already action-scoped so adding roles later is additive.
- A dedicated enterprise secrets/HSM integration — MVP uses one pluggable secrets-manager interface; swapping the backend doesn't change any calling code.
- Network egress allowlisting per project — MVP uses a conservative default sandbox policy; per-project policy is a config addition to the same Workspace abstraction, not a new layer.

See [MVP_SCOPE.md](./MVP_SCOPE.md) for the explicit in/out boundary.

## Backlog analysis: model output is a proposal *(Phase 4A)*

The same rule as reviewer verification — "AI can make claims; CodeForge owns evidence and state" — governs backlog analysis ([BACKLOG_INTELLIGENCE.md](./BACKLOG_INTELLIGENCE.md) §2). A model's analysis is schema-validated with **strict** objects (any unknown key, including one naming a status/approval/task id/retry limit/validation/branch control, makes the output malformed and it is discarded); it is only ever *read*, never executed; the platform alone derives item status and builds the task proposal; approval and conversion exist only as authenticated owner actions; conversion uses the existing `TaskService.create`, so the resulting Task is an ordinary `BACKLOG` task that still needs an explicit Start. Analysis runs in the **worker** process (Phase 4A.1) — the API process holds no engine or analyzer at all, so a request can never cause a model call; every result write is fenced by the job's claim (owner + lock generation) in one transaction, so a stale worker cannot overwrite or duplicate a result, and a database-coordinated global cap bounds live model calls. The analysis engine runs in an empty throwaway directory, never a repository or task workspace; the repository listing that informs it is produced with the project's own env-only clone credential in a temp directory that is always removed and contains no file contents. Every backlog/proposal route is owner-only with `404` for foreign ids (IDOR-tested); relationship references resolve only within the same project, so one project's items are never shown to a model analyzing another's. Failure text and malformed-output excerpts pass through `redactSecrets` and are bounded. Untrusted item text is delimited as data in the prompt — defense in depth, not the boundary.

### Backlog analysis: evidence is platform-owned and repository reads are bounded *(Phase 4A.2)*

The model can only *assert*: its output has no evidence, verification or verdict field (a strict schema rejects any), and a claim's status is a pure function of evidence the platform obtained (`assessClaims`) — free-text words such as "verified" are inert, and a `high` stated confidence never overrides a contradiction (it forces `NEEDS_CLARIFICATION` and is exposed). Repository content reaches a model only through `RepositoryInspector`: chosen by the platform, read from the git object store by exact listed path (nothing is checked out, so no path traversal and no symlink following — symlink and submodule entries are refused), capped at 12 files / 64 KiB per file / 256 KiB total / 30 s, with secret-bearing paths (`.env*`, keys, certificates, credentials, `.ssh`/`.aws`…) never read, files containing a private-key marker discarded, credential-looking values masked in every excerpt and evidence line, and every skipped file recorded. No shell and no network access beyond the read-only clone and per-blob reads. Verified by unit tests, tests against real git objects (symlink, `.env`, binary, oversized), and mutation testing of each guard.

### Backlog analysis: the repository index is derived, revision-bound and inert *(Phase 4A.3)*

The repository index ([BACKLOG_INTELLIGENCE.md](./BACKLOG_INTELLIGENCE.md) §4b) is a **cache of facts about one commit**, not a source of authority.

- **Platform-generated only.** Built by platform code from file content read through the same `RepositoryInspector` as every analysis read — so secret paths, private-key markers, binaries, symlinks, submodules, size and time limits apply identically. Secret-named files are excluded from the index entirely; the stored document holds identifiers, route strings and paths, never file bodies. Nothing a model returns can write to it.
- **Cannot cross a boundary.** Rows are keyed `(project_id, source_key, revision, schema_version)`; `source_key` hashes repository URL + branch. Project B never reads project A's index even for the same repository; a stale revision is a cache miss, and `indexMismatch` re-checks revision/source/schema before use (a mislabelled row is `rejected`, not used). Deleting a project deletes its index rows.
- **Cannot control anything.** The index reaches a model only as a ranked list of paths inside a labelled data block, and reaches the evidence layer only as existence evidence (`SYMBOL_MATCH`). It is never read by the orchestrator, task creation, retry limits, approval, or conversion; symbol/route text that reads like an instruction ("approveProposal", `/IGNORE_ALL_RULES`) is data (covered by `tests/backlog-index.test.ts`).
- **No indexing storm.** One build per (project, source, revision) — coordinated by the row (live claim ⇒ others degrade to name-only selection, never wait or duplicate), bounded (900 files / 8 MiB / 180 s) and run inside an existing lease-, cancel- and concurrency-capped analysis job.
- **Execution stays platform-owned.** The verification seam ([BACKLOG_INTELLIGENCE.md](./BACKLOG_INTELLIGENCE.md) §4c) is disabled in production analysis. Were it enabled it would run only a check the project itself configured, chosen by the platform (never by a claim or by index content), against a workspace proven to be at the analysed revision, under the existing timeout/cancellation; the model's strict output schema has no field that could name a command, and injected ids are refused before a process is spawned.

### Backlog analysis: reconciliation is platform-owned and revision-bound *(Phase 4A.4)*

Reconciliation ([BACKLOG_INTELLIGENCE.md](./BACKLOG_INTELLIGENCE.md) §4d) is a pure function of the AI's claims and evidence the platform obtained — the strict analysis schema has no field through which a model could supply a reconciliation, verification, or command (`tests/backlog-reconciliation.test.ts`). Evidence is stamped with the revision it describes; evidence for any other revision (stale index, stale `CHECK_RESULT`) is ignored, so evidence from revision A cannot reconcile a claim analysed at B. Secret files, symlinks and submodules stay excluded from every evidence path (the same `RepositoryInspector`). A "conflict" signal only reframes a proposal as an investigation; approval and conversion remain explicit human actions, and nothing starts a task. **Usage integrity:** unavailable usage is `null` (never zero), partial usage is labelled `partial` (never `complete`), and a priced part merged with an unpriced part yields no estimate rather than a fabricated total.
