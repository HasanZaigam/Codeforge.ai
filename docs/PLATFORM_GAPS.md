### Phase 4D.2.1 status updates (real-world incident: action detection was too narrow, letting a false completion claim leak through)

**GAP FOUND AND FIXED — a real Review task in a live browser session got a false "I have updated the status ... to completed" response from Chat.** Root cause was NOT a flaw in `ActionLayerService`'s read-back verification (Phase 4D.2's fix held) — it was that `chat-intent.ts`'s `ACTION_MARK_DONE` pattern only recognized the literal phrase "mark ... done/complete/completed". The real message, "make the review task add profile to done", used none of those words, so `parseIntents` classified the entire message as a plain `UNSUPPORTED` clause with no `isActionFailure` flag, `answerDeterministically` returned `null` (nothing recognized), and the message fell through to the general free-text `answerText`/`BacklogAnalyzer.run` path — which has no mutation capability at all but fabricated a plausible-sounding "I have updated..." sentence anyway. The real task never left `REVIEW`.

**Fixed in two layers, per the phase's own "enforce in code, not only by prompting" requirement:**
1. **Primary fix — broadened action-language detection.** `ACTION_MARK_DONE`'s pattern now recognizes the natural completion verbs people actually use (mark/make/set/move/close a task done/complete/completed/finished, "complete `<task ref>`", "is resolved") instead of only the one literal phrase. Also added a REVERSE fuzzy title match (`extractReferencePhrase` + `resolveActionTarget`'s new fallback step): the real task's title was far longer than what the user typed ("Add profile (+) option still shown after reaching the maximum number of profiles...' vs. "add profile"), and the original resolver only checked whether the CLAUSE contained the FULL title — never the reverse. And "make the OLDEST Review task Done" now resolves its target via the same oldest-in-status lookup the read path already uses, rather than asking the title matcher to somehow parse "oldest". None of this adds a new lifecycle transition — `ActionLayerService.markDone` still always honestly declines from REVIEW, exactly as Phase 4D.2 left it.
2. **Defense in depth — a code-level scrubber on the free-text path itself.** Even with broadened detection, the free-text `answerText` path is open-ended and could in principle still be reached by some other unrecognized mutation phrasing. `ChatService` now regex-scans that path's raw model output for a first-person completed-mutation claim ("I('ve| have) updated/marked/changed/cancelled/started/completed/closed/resolved/moved/...") and replaces it with an honest "I can't make changes to tasks through general conversation" message before it ever reaches the user — since that path genuinely has no mutation capability, any such claim from it is false by construction, not a borderline case requiring judgment.

**No new gap found in `ActionLayerService` itself, or in the audit trail.** Confirmed no `CHAT_ACTION_PERFORMED` event is ever created for the declined case, and the real task's status is untouched in every regression test.

Regression coverage: `tests/chat-action-fallback-safety.test.ts` (11 tests) — the exact reported phrase, 5 natural variants ("mark the review task add profile done", "make the add profile task done", "move the add profile task to done", "set the add profile task to completed", "complete the add profile review task"), a no-tasks-in-status edge case, a multi-intent read+action message, a hedged/conversational statement that must NOT mutate, existing supported actions (create/start/cancel/rename, including an id-addressed start) confirmed still working, and a direct test of the code-level scrubber. Full backend suite (1162 pre-existing + 11 new = 1173 tests) run to confirm no regressions; typecheck/build clean; `git diff --check` clean.

### Phase 4D.3.1 status updates (real-world incident: clause splitting broke a task title containing a bracketed bug-id list)

**GAP FOUND AND FIXED — a task reference + action request was shredded by the multi-intent clause splitter's naive comma handling.** The real message, `"Add profile (+) option still shown after reaching the maximum number of profiles (BUG-036, BUG-037) make this task from review to done"`, contains a task title with a bracketed bug-id list. The old `splitIntoClauses` split within a sentence using `.split(/,\s*and\s+|\s+and\s+|,\s+/)` with no awareness of parentheses — so it split right at the comma INSIDE `(BUG-036, BUG-037)`, breaking the title into two fragments, neither of which could resolve to the real task via the existing exact-substring/fuzzy-match logic. The whole message surfaced as two garbled "I couldn't answer: '...(BUG-036'" / "'BUG-037) ...'" clauses — never reaching `ActionLayerService` at all, so this was a **parsing bug upstream of task resolution and the Action Layer**, not a flaw in either.

**Root cause confirmed precisely**, not just inferred from the symptom: traced to the exact `.split()` call in `splitIntoClauses`, verified by reproducing the identical two-fragment output in a unit test before writing the fix.

**Fixed with a context-aware splitter, not a blanket "stop splitting on commas" change** (which would have broken legitimate multi-intent commas like "How many tasks are in Review, and which is the oldest?"):
1. `splitRespectingNesting` — a character-by-character scanner tracking `(...)`/`[...]` nesting depth and `"..."`/`'...'` quote state; a comma/"and" is only ever treated as a clause boundary when it occurs OUTSIDE all of them.
2. `maskBugIdListCommas`/`restoreMaskedCommas` — a bug-id list with NO surrounding brackets at all ("BUG-036, BUG-037" bare in running text) is pre-masked before splitting, since bracket-depth tracking alone can't protect a comma with nothing around it.

**No new task-resolution mechanism was needed — and none was added.** Once the clause survives intact, it contains the task's FULL real title as a literal substring, so `resolveActionTarget`'s EXISTING exact forward-substring check (Phase 4D.2) resolves it directly; a shortened reference ("the Add profile (+) option task") resolves via the EXISTING reverse fuzzy match (Phase 4D.2.1). **No Review→Done transition was added, and the Task state machine was not touched** — `ActionLayerService.markDone` already honestly declines a Review task exactly as Phase 4D.2 left it; this fix only had to let the real request reach that existing, correct decline instead of getting shredded before it ever arrived.

Regression coverage: `tests/chat-clause-splitting.test.ts` (18 tests) — 11 direct unit tests on `splitIntoClauses` (the exact reported message, a bracket-less bug-id list, a three-item list, plain-parenthetical/bracket/quoted commas, ordinary multi-intent commas still splitting correctly, a bug-id list followed by a real second request still splitting at the true boundary, the pre-existing status-enumeration case, and titles with `:`/`-`/`/` confirmed unaffected), plus 7 end-to-end tests through the real `sendMessage` pipeline covering the exact incident and all 4 of the brief's phrasing variants ("make/move/complete ... done"), the bug-id-list read phrasing, and both multi-intent regression cases. Four real, live-reported failures this phase fixes, verified against this phase's own test suite (`tests/phase4d6.test.ts`, `tests/phase4d61.test.ts`, `tests/phase4d62.test.ts` — 15 tests):

### Model Gateway — real browser-reported gaps found live-testing "Load models" against a real Google key

Three distinct, real issues surfaced testing the "Load models" feature in the browser (none caught by the scripted-adapter unit tests above, since those deliberately never make a real network call — see that phase's own "Verified, not claimed" note):

1. **A bare "fetch failed"** — Node's `fetch` (undici) can attempt an IPv6 route first and fail outright on a network where IPv6 is advertised but not actually routed, even though the same host is reachable over IPv4 (confirmed: `curl` and a direct one-off `node -e fetch(...)` both succeeded from the same machine while the running API process's own call failed). **Fixed** with `dns.setDefaultResultOrder("ipv4first")` at API-server startup (`src/api/server.ts`) — Node's own documented fix for this exact class of flake, applying to every outbound fetch the process makes, not a provider-specific workaround — plus a one-shot retry-on-network-failure-only wrapper (`fetchWithRetry` in `src/providers/provider-adapter.ts`) as a second layer of resilience.
2. **A genuinely invalid key was reported as a vague "Google returned an unexpected error (HTTP 400)"** instead of an actionable "your key is wrong." Root cause: Google's Generative Language API returns HTTP 400 (not 401/403) for `API_KEY_INVALID` — confirmed live by calling the real endpoint directly with a clearly-fake key and reading the actual response body, which the adapter wasn't parsing at all for non-401/403 errors. **Fixed** by parsing the real error body's `reason`/`status` fields and surfacing the specific, correct guidance ("Create one at aistudio.google.com/apikey...") instead of a generic HTTP-code message.
3. **A real, currently-issued, genuinely working Google API key was still rejected with `API_KEY_INVALID`** even after fix #2, because the adapter authenticated via the older `?key=<value>` query-string convention — confirmed live, with the user's own real key, that Google's API accepts this exact key via the `X-goog-api-key` HEADER but rejects the identical key via `?key=`. **Fixed** by switching the adapter to send the key exclusively via `X-goog-api-key`, Google's current documented mechanism, for every key (not a format-conditional branch). This was the actual root cause the first two fixes had not yet addressed — live-verified end-to-end afterward: the same real key correctly returned a real list of ~30 available Gemini models.

**Process note, not a code gap**: a stale `npm run api` process (started before the "Load models" feature was finished — this repo's own documented `tsx` hot-reload gotcha, see Phase 4D.1) also produced a misleading "fetch failed" symptom at one point during this same debugging session, independent of the three real issues above; restarting resolved it immediately and is noted here only so a future debugging session checks process freshness FIRST, before chasing a network-layer explanation.

**Security note**: during live debugging, the user pasted a real, working Google API key into chat text twice (once as a bare string, once inside a curl snippet copied from Google AI Studio's own code sample) — the second paste was what correctly exposed root cause #3 above (the adapter's `?key=` vs `X-goog-api-key` bug), but using it for that one-off diagnostic call also means that key is now considered exposed; the user was told explicitly to rotate/regenerate it.

Regression coverage: `tests/model-gateway.test.ts` re-run in full after each of the three fixes (22 tests, zero regressions each time — the 22nd, `listAvailableModels`, was added in the same session as the "Load models" feature itself, see above). Full backend suite re-run after fixes #1/#2: 1302/1302 passing. Fix #3 (the actual root cause) does not change any unit-testable branch the scripted-adapter suite exercises (the fix is in the literal auth transport, not an error-handling branch) — its correctness was verified live, directly against the real Google API, both before the fix (confirmed rejected) and after (confirmed accepted, real model list returned).
