

## 4p. Run-scoped review packages *(Phase 4B.4)*

A bulk analysis run (`BulkJobRecord.id`) IS the "run identity": `sampleDuplicateGroups`/`sampleClarification`/`sampleProposalReady`/`createBaseline` all take an optional `runId` that restricts every sample to that run's own **successfully analysed** members — a member whose own claim on the item did not succeed (even if the item happens to have a valid analysis from elsewhere) is never a candidate; a duplicate edge is included only when BOTH endpoints are run members. A run's FAILED/SKIPPED/CANCELLED members are collected separately as `infrastructureFailures` (item, ref, title, failure category/reason) — never as a duplicate/clarification/proposal-ready candidate, and never silently dropped. `createBaseline({ runId })` validates the run belongs to the given project up front, and — if the run produced a non-empty sample — refuses to freeze unless at least one real repository revision was captured (`"Repository revision discrepancy…"`), so a run that silently degraded to text-only (the exact Phase 4B.3 root cause) can never be mistaken for a repository-aware baseline again. The frozen baseline's `sample.runId`/`infrastructureFailures`/`requestedSampleSizes`/`actualSampleSizes` make exactly what was reviewed, and what was excluded and why, part of the permanent record. The UI (`AdjudicationPanel`) shows a **CORRECTED REPOSITORY-AWARE RUN** banner with revision/model/sample counts/excluded-failure count whenever a baseline names a `runId`.

## 4q. Persisting a run for real human review: `--keep-db`/`--resume` *(Phase 4B.5)*

`npm run validate:adjudication` (fresh-run mode) always deleted its scratch database (`rmSync(scratch, ...)`) once it finished — including the bulk job, its analyses, its frozen baseline, and the sample it had just printed. This meant no run the CLI ever produced, including the run named at the top of Phase 4B.5's own brief (`523be057-d9cc-4416-9e25-2eabf990c9f9`), could still exist by the time a human reviewer sat down to fill in the template: the database backing it was already gone. A genuine infrastructure gap, not a data-quality one — the review workflow (sampling, baselines, judgments, staleness) was correct throughout Phase 4B.1–4B.4; it simply had nothing durable to point a human reviewer at.

Fixed with two new flags on the fresh-run path, both optional and backward compatible:
- `--keep-db <dir>`: instead of deleting the scratch database at the end, copies it to `<dir>` and prints the exact `DB_PATH=... npm run api`/`npm run worker` commands (naming the project id to log into) plus the `--resume` invocation to keep applying labels later. Omitting it preserves the original (destructive) behavior, with an explicit warning printed that the run is about to become unrecoverable.
- `--resume <dir>`: reopens a `--keep-db` directory **in place** (points `DB_PATH`/`WORKSPACES_ROOT`/`PROJECT_WORKSPACE_ROOT` directly at it, no copy), resolves the project/run (explicit `--project-id`/`--run-id`, or the most recent of each), re-samples (identical, since sampling is deterministic from stored data), applies any `--apply <filled.csv>` file, and freezes a new baseline version — all **without re-running any real-model analysis**. Both the fresh-run path and `--resume` funnel through the same shared `sampleApplyReport()` helper, so their report JSON is identical in shape.

Verified end-to-end against a real Jinvani run (`a3413089-10b9-4fd9-b685-327c94cc4ece`, see §24): `--keep-db` preserved a ~106 MB working database after the real run completed; a subsequent standalone `--resume` invocation against that preserved directory reopened it, reproduced the exact same deterministic sample (8/12 duplicate groups, 15/56 clarification, 10/20 proposal-readiness), and froze a new baseline version — with zero calls to the real model. This makes real human ground-truth review structurally possible for the first time; before this fix, every "real" validation run in Phases 4B–4B.4 was disposable by construction.
