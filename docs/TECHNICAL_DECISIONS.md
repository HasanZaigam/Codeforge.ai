

## TD-60: Model Gateway — a narrow interface keeps the Orchestrator from depending on the application layer

Introducing a per-account Model Gateway (see docs/MODEL_GATEWAY.md) needed the Orchestrator and BacklogAnalyzer — both below `src/application/` in this codebase's layering (TaskService holds `platform.orchestrator`, never the reverse) — to resolve a `ModelSelection` through it. The straightforward approach (have `Orchestrator` import the concrete `ModelGatewayService` class from `src/application/model-gateway-service.ts`) would have been the first time `src/orchestrator/` depended on `src/application/`, inverting the existing dependency direction. The fix follows a pattern this codebase already established for the exact same problem one layer down: just as `ProviderHealthLookup` (`routing/provider-health-policy.ts`) lets `selectModel` stay independent of the concrete, SQLite-backed `ProviderHealthRepository`, a new `ModelGatewayLookup` interface (`routing/model-router.ts`) declares only the one method (`resolveModelSelection`) the Orchestrator/BacklogAnalyzer actually call. `ModelGatewayService` implements it structurally; both lower-layer consumers depend on the interface, never the concrete class. (`platform.ts` itself already imports and constructs concrete `application/`-layer classes directly — `BacklogAnalysisExecutor`, `BacklogServiceOptions` — so constructing `ModelGatewayService` there, alongside `backlogAnalyzer`, and injecting it into both at construction time was consistent with existing precedent; only the Orchestrator's own internal dependency needed the interface indirection.)

A second, smaller decision in the same feature: a Fixed global AI brain naming a disconnected provider must never silently fall back (Failure/Fallback Rules) — but `BacklogAnalyzer.run()`'s established contract is to never throw, always returning an `AnalyzerOutcome`, while `Orchestrator.runAgent()` already lets thrown errors propagate into its own `TASK_FAILED` handling. Rather than force one contract onto the other, `ModelGatewayService.resolveModelSelection` throws `ModelGatewayResolutionError` for this one case, and each caller handles it the way it already handles every other failure in its own control flow: the Orchestrator lets it propagate; the BacklogAnalyzer catches it immediately and returns an honest `{ok: false}` outcome. No new failure-handling contract was invented for either.

## TD-59: A durable audit record must never hold a live row hostage; staleness is computed against LIVE state, not sample time

Phase 4B.1's `backlog_relationship_judgments` FK on `relationship_id` looked like ordinary referential integrity but actually violated the layer's own stated design: a judgment must "become stale, never silently reattached" — which requires the live relationship to be free to disappear or be replaced. A hard FK instead let a single human judgment block an entire future re-analysis with a raw constraint error. The fix (migration 021: rebuild without the FK) generalizes: **any append-only ground-truth/audit table referencing a row that ordinary application logic deletes or replaces must not enforce that reference at the database level** — it must denormalize what it needs (Phase 4B.1 already did, for exactly this reason) and treat the live row as optional context, not a dependency. Staleness itself is computed by comparing a judgment's own `analysisId` to whatever is LIVE right now (the item's latest succeeded analysis, or the relationship's own current `analysisId`) — never to what the sample happened to look like at read time — so it stays correct regardless of how many times a target has moved on since.
